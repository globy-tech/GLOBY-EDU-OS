# Backend

Purpose: Hosts REST/GraphQL APIs, background workers, and service orchestration.

Architecture notes:
- Use clean architecture and hexagonal style (controllers, services, repositories).
- Keep infra code separate from business logic.
- Favor small, well-tested modules.

This README is a placeholder for backend design and conventions.

## Isolated local JSON data

For a development-only test instance, set `DATA_STORE_MODE=json` and optionally
set `GLOBY_SCHOOLS_FILE` to a separate JSON file path. This keeps that instance's
school records out of `backend/data/schools.json`. Do not use JSON storage in
production; production requires Firebase.

### Isolated local QA instance (Windows)

Run `npm run qa:provision` once to create synthetic school, class, teacher,
student, assignment, and platform-admin fixtures under
`%LOCALAPPDATA%\GlobyEdu-QA`. The command refuses to overwrite an existing QA
folder. It writes the generated QA-only login details to `accounts.txt` in that
folder; keep that file private.

Run `npm run qa:start` to start the QA server on port 4001. The QA process uses
only the explicit stores under that QA folder, disables automatic development
demo-account seeding, and refuses production, database, or repository-local
data-store configuration. QA pricing uses a synthetic in-memory plan; pricing
edits, checkout, payment verification, webhooks, and refunds are disabled. The
launcher removes and the server rejects Firebase, database, file-storage,
payment-provider, and transactional-email credentials so QA does not connect to
those external services. The regular development server and its port 4000
configuration are unchanged. QA
records persist between runs; no reset command is provided. Stop the foreground
server with Ctrl+C; this does not stop the separate development server.

## File uploads

Authenticated file uploads are limited to 20 MiB per file across the frontend
and API. Images are uploaded at their original quality; the application does
not resize or recompress them. Uploads are tenant-scoped and stored in cloud
storage: production requires Cloudflare R2, while development uses configured
Firebase Storage or the storage adapter (R2/Supabase). Signed download URLs are
generated by the API. Live production storage credentials and R2 upload/
retrieval must be verified in an approved environment before release.

## Class, teacher, and student workflows

Tenant-scoped records use `/api/v1/schools/:schoolId/entities/:entityType`.
Class records may include `academicYearId`, `section`, and `teacherIds`.
Duplicate class identity is rejected within an academic year; explicit
`academicStructure.classAliases` configuration controls which class labels are
equivalent. A teacher sees and manages students only for assigned classes.
Firebase student creation uses create-only student/account records and reports
partial-write cleanup failures instead of returning a success response.

The Prisma class-field migration is documented in
`database/prisma/migrations/README.md` and remains unapplied. Admissions
conversion and student progression are available as tenant-scoped workflows.
Progression exposes preview and confirmation endpoints; class paths,
graduation classes, and class aliases are configured per school. It reuses the
existing student identity and enrollment history and does not require a new
schema migration. Holiday calendars and automatic teacher attendance tasks
are not currently exposed as dedicated workflows.

## Production configuration contract

Configure these values in the production secret manager; never commit them or
copy values from a developer machine:

- `NODE_ENV=production` and `DATA_STORE_MODE=firebase` are required. The server
	rejects production startup in JSON/Prisma mode.
- Firebase Admin requires `FIREBASE_PROJECT_ID` and either both
	`FIREBASE_CLIENT_EMAIL` plus `FIREBASE_PRIVATE_KEY`, or explicitly provisioned
	Application Default Credentials (`GOOGLE_APPLICATION_CREDENTIALS` where
	applicable). The Firebase web client config is public, not a secret:
	`FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, and
	`FIREBASE_APP_ID`; `FIREBASE_MESSAGING_SENDER_ID` and
	`FIREBASE_STORAGE_BUCKET` are optional according to enabled client features.
- `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` must be distinct, strong,
	non-default values. `APP_URL` must be the canonical HTTPS application URL.
- `CORS_ORIGINS` is a comma-separated allowlist for any browser origins outside
	the built-in GlobyEdu domains. Production browser origins must use HTTPS;
	localhost origins are allowed only outside production. `COOKIE_DOMAIN` is optional and should only be
	set when the app/API host topology requires a shared cookie domain. Refresh
	cookies use `HttpOnly`, `Secure`, and `SameSite=Strict` in production; the
	frontend/API must remain same-site for refresh-cookie delivery.
- Production file storage requires `CLOUDFLARE_R2_ACCOUNT_ID`,
	`CLOUDFLARE_R2_ENDPOINT`, `CLOUDFLARE_R2_ACCESS_KEY_ID`,
	`CLOUDFLARE_R2_SECRET_ACCESS_KEY`, and `CLOUDFLARE_R2_BUCKET`.
	`CLOUDFLARE_R2_PUBLIC_URL` is optional; the application can serve private
	files through short-lived signed URLs without a public bucket URL.
- Transactional mail uses Brevo when both `BREVO_API_KEY` and
	`BREVO_SENDER_EMAIL` are configured. Resend is the configured alternative and
	fallback for Brevo client rejections when `RESEND_API_KEY` and
	`RESEND_FROM_EMAIL` are configured; it is not retried on ambiguous server or
	network failures to avoid duplicate delivery. The public contact endpoint
	uses this same provider service and additionally requires `CONTACT_EMAIL` as
	its destination. Provider acceptance is not proof of inbox delivery;
	sender-domain verification and DNS records must be completed by the domain
	owner. Contact submissions are limited in-process to five per IP per 15
	minutes; multi-instance deployments should also configure edge-level limits.

`CLOUDFLARE_R2_PUBLIC_URL`, `BREVO_SENDER_NAME`, and `COOKIE_DOMAIN` are optional.
Do not invent sender identities, contact destinations, DNS records, or secrets.
