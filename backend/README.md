# Backend

Purpose: Hosts REST/GraphQL APIs, background workers, and service orchestration.

Architecture notes:
- Use clean architecture and hexagonal style (controllers, services, repositories).
- Keep infra code separate from business logic.
- Favor small, well-tested modules.

This README is a placeholder for backend design and conventions.

## Isolated local JSON data

For a development-only test instance, set `DATA_STORE_MODE=json` and optionally
set `GLOBY_SCHOOLS_FILE` to a separate JSON file path. This keeps that instance's
school records out of `backend/data/schools.json`. Do not use JSON storage in
production; production requires Firebase.

### Isolated local QA instance (Windows)

Run `npm run qa:provision` once to create synthetic school, class, teacher,
student, assignment, and platform-admin fixtures under
`%LOCALAPPDATA%\GlobyEdu-QA`. The command refuses to overwrite an existing QA
folder. It writes the generated QA-only login details to `accounts.txt` in that
folder; keep that file private.

Run `npm run qa:start` to start the QA server on port 4001. The QA process uses
only the explicit stores under that QA folder, disables automatic development
demo-account seeding, and refuses production, database, or repository-local
data-store configuration. QA pricing uses a synthetic in-memory plan; pricing
edits, checkout, payment verification, webhooks, and refunds are disabled. The
launcher removes and the server rejects Firebase, database, file-storage,
payment-provider, and transactional-email credentials so QA does not connect to
those external services. The regular development server and its port 4000
configuration are unchanged. QA
records persist between runs; no reset command is provided. Stop the foreground
server with Ctrl+C; this does not stop the separate development server.

## File uploads

Authenticated file uploads are limited to 20 MiB per file across the frontend
and API. Images are uploaded at their original quality; the application does
not resize or recompress them. Uploads are tenant-scoped and stored in cloud
storage: production requires Cloudflare R2, while development uses configured
Firebase Storage or the storage adapter (R2/Supabase). Signed download URLs are
generated by the API. Live production storage credentials and R2 upload/
retrieval must be verified in an approved environment before release.
